# Curve の stable ID スパイク結果

実施: 2026-10-01 / Blender 5.1.1(Windows、`-b` のバックグラウンド実行)
再現: `scripts/spikes/` の各スクリプトを `blender -b --factory-startup --python <script>` で走らせる。
4.2.7 でも操作の一覧(`bpy.ops.curve` / `bpy.ops.curves`)は同じ。挙動の実測は 5.1 のみ。

目的は「Muslin が要る semantic identity(点の同一性)を、Blender 標準の編集操作を使いながら
維持できるか」の確認。点ごとに radius / tilt / weight_softbody(従来型)、または INT 属性
(Curves)に目印を仕込み、各編集操作のあとに残り方を見た。

## 従来型 Curve(`bpy.types.Curve`)

| 操作 | index | 目印の残り方 |
|---|---|---|
| 点の移動 | 不変 | 不変 |
| extrude(末尾・cyclic の点) | 点が増える | **新しい点が元の点の値を複製** |
| subdivide | 点が増える | 新しい点は**両隣の線形補間**(radius 20 と 30 の間 → 25) |
| delete / dissolve | 後ろの index が詰まる | 残った点は不変 |
| split | 選択が別 spline になる | 境界の点が**複製**され、両方の spline に同じ目印が出る |
| separate(別オブジェクト) | 元と新で別々に振り直し | 境界の点が複製される |
| make_segment(2 spline をつなぐ) | 1 本になる | 不変(順序も保たれる) |
| cyclic_toggle | 不変 | 不変 |
| switch_direction | 並びが逆順 | radius / weight は不変、**tilt は符号が反転** |
| **delete SEGMENT(cyclic)** | **始点が回転**(index がずれる) | 不変 |
| duplicate | 新 spline を末尾に追加 | 複製 |
| decimate | 点が減る | 残った点は不変 |
| Object 複製 | 不変 | 不変。Curve データのカスタムプロパティも複製される |
| Object join | 相手の spline が末尾に付く | 不変(オブジェクト間で目印は衝突しうる) |
| .blend 保存・再読込 | 不変 | 不変。Curve データのカスタムプロパティも残る |
| Undo / Redo | **未確認**(バックグラウンドでは効かない) | 手動確認が必要 |

- **index は恒久 ID にならない。** 点の削除・cyclic の辺の削除(始点が回転)・split・join で動く。
  spline の順序も separate / split / duplicate で変わる
- **Spline / 点にカスタムプロパティは持てない**(`id properties not supported`)。
  spline には ID を持たせる手段がなく、ID を持てるのは Curve データ全体だけ
- 点ごとの float 3 つ(`radius`, `tilt`, `weight_softbody`)は、編集操作を通しても**値は動く点に付いて回る**。
  ただし新しく生まれる点は「複製」か「補間」になる
- 値域: `radius` は 0 以上で float32 の整数を 2^24 まで正確に持てる(負数は 0 に丸められる)。
  `weight_softbody` は 0.01〜100 に丸められる。`tilt` は約 ±377 で丸められる

## 新しい Curves データ(`bpy.types.Curves`)

- 点(POINT)・カーブ(CURVE)ごとに任意の INT 属性を持てる。API は素直
- **属性の振る舞いは従来型と同じ**: subdivide は線形補間(整数属性でも 15, 25 のような値になる)、
  extrude / duplicate は複製、delete は残った点に不変、switch_direction は順序だけ反転、
  CURVE ドメインの属性は split / duplicate で複製される
- 従来型にない利点は 2 つだけ: 専用の属性を持てる(radius 等を借りなくてよい)、
  カーブ(= ピース)ごとの属性を持てる
- 欠点: 手動で作った Bezier だと編集操作が**アクセス違反で Blender が落ちた**。
  `bpy.ops.curves.add_bezier`(編集モード内)で作った正規のデータなら動く。
  `split` は今回の合成データで落ちた(原因未調査)。2D の面塗り表示が無い。
  編集の操作性(ハンドル、ペンツール)は従来型が成熟している
- 結論として、**同一性の維持という基準では従来型に対する優位がない**

## 結論

1. **どちらのデータでも、標準の編集操作の下で「点の恒久 ID」は自動では保たれない。**
   保たれるのは「既存の点の目印が点に付いて回る」ことまで。新しい点は複製か補間になる
2. ただしその挙動は**検出できる**。複製 = 同じ目印が 2 点に出る、補間 = 既知の 2 点の間に
   中途半端な値の点が出る。「既存の点は同一性が保たれ、新しい点は検出できる」なら、
   `セグメントが分割された / 点が増えた` を**推測ではなく検出**として扱える
3. 従来型 Curve を採る。データの成熟度と、「新しい API だから」ではなく同一性で見て差が
   無いことが理由。Curves への移行は将来の選択肢として残す(§下記の抽象化で塞がない)

## 従来型での目印の運び方(採用案)

- `radius` に uid(1〜2^24 の整数)、`weight_softbody` に検算値(uid の非線形ハッシュ、0.01〜100)を書く。
  型紙は 2D なので radius(ベベル用)と softbody の重みは使わない
- **検算値は非線形にする**。線形(黄金比の小数部など)だと補間しても一致してしまい、
  補間で生まれた点の約 25% が正規の点に見えた。非線形なハッシュにすると誤認は 20 万回中 3 回
  (`scripts/spikes/check_uid_scheme.py`)。許容誤差を float32 の精度ぎりぎりまで絞ればさらに減る
- 読み取り時の分類:
  - 検算が合う、かつ uid がその Curve 内で一意 → **既知の点**
  - 検算が合わない → **新しい点(補間または手描き)**。前後の点が既知なら、その間の区間が分割されたと検出できる
  - 同じ uid が 2 点以上 → **複製**。ひとつを元、残りを新しい点として扱うが、どちらが元かは決められないので
    **Rebuild Required + 要確認**にする
- tilt は switch_direction で符号が反転するので目印には使わない(向きの反転の検出には使える)
- spline には ID を持てないので、**ピースの同一性は所属する点の uid から導く**
  (ピース uid 表を Curve データ側に持ち、spline の点の uid の集合で当てはめる)
- 目印の書き方・読み方は 1 か所のモジュールに閉じ、後で Curves に替えられるようにする

## Blender 4.2.7 での実測

従来型 Curve のスパイクを 4.2.7 でも走らせ、5.1.1 と比べた。ほぼ一致するが、**subdivide の補間だけ違う**。

- 1 分割: radius / weight は線形補間で同じ。**tilt が線形ではなく段階的**(0.25 ではなく 0.30)
- 2 分割以上: 5.1 は線形(13.33, 16.67)だが、4.2 は**段階的**で、隣り合う新しい 2 点が同じ値
  (radius 15 が 2 つ)になる。目印の uid が新しい点どうしで重なる

新しい点の値が uid として通ってしまうかは検算値で決まる(新しい点の検算値は補間・段階どちらでも
ハッシュと一致しない)ので、分類は成り立つ。ただし**新しい点が 2 つ同じ uid で現れる**ので、
「複製」ではなく「検算が合わない点」を先に判定する(uid の重複判定は検算が合った点だけに使う)。
